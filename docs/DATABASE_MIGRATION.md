# Database migration and preservation

The source database is MySQL/MariaDB revision 543 with 281 baseline tables.
Production data must never be pointed at autogenerated replacement migrations.
The present PostgreSQL schema is an isolated development target, not a complete
mapping and not authorization to discard legacy columns.

## Strategy

1. Treat `openemr-legacy/sql/database.sql`, `db/`, installed-site schema and
   upgrade scripts as authoritative, in that order when production differs.
2. Inventory every table, column, key, index, default, enum, trigger and view.
3. Land additive target migrations and idempotent import adapters with stable
   `legacy_*` identifiers. Store unmapped values losslessly until typed.
4. Reconcile source/target row counts, foreign-key orphans, monetary totals,
   document hashes and representative workflow results before cutover.
5. Run repeatable snapshots, dual-read comparison and rollback rehearsals.

## Current entity map

| Legacy tables | Target model | Transformation / compatibility risk |
|---|---|---|
| `users`, `users_secure`, `gacl_*` | User and policy models | Preserve usernames, account state, hash algorithm metadata and complete ACL graph; never flatten ACL to one role |
| `patient_data`, `layout_options` DEM rows, `list_options`, `person*`, `contact*`, `addresses`, `phone_numbers`, `employer_data` | `patients`, normalized contact/history models, `patient_consents`, `patient_custom_field_definitions`, `patient_custom_field_values` | Core identity and common workflows are typed. Guardian/mother columns become idempotent related-person records while retaining complete source values and never inferring legal authority. Eleven consent fields become versioned records. Every DEM layout definition and column-backed value is retained without coercive loss. Each import now reports direct typed-field and complete `legacy_payload` matches/mismatch PIDs plus a deterministic reconciliation checksum; a zero-mismatch production-source report remains a cutover gate. |
| Duplicate patient charts | `patient_merges`, retired `patients.merged_into_id` aliases | Reviewed consolidation locks both charts and atomically moves dependent records. The evidence row retains reviewer, reason, match fields, per-table counts and uniqueness-conflict snapshots. Retired portal identities are disabled and their sessions revoked; subsequent imports resolve legacy aliases to the canonical chart. |
| `patient_access_onsite`, `onsite_mail`, `onsite_messages`, `pnotes`, `form_taskman`, `email_queue` | `portal_accounts`, `message_threads`, `secure_messages`, `clinical_tasks`, `communication_deliveries` | Patient identities remain separate from staff users; resolvable messages and tasks retain source payloads. Legacy password and one-time verifiers are intentionally discarded, replaced by random unusable hashes, and require a modern password reset. Unresolvable recipients are counted as rejected. |
| `openemr_postcalendar_events`, `patient_tracker*` | `appointments`, `patient_flow_episodes`, `patient_flow_events` | Appointments preserve core times, category, provider/facility/room, contacts, reminder intent, legacy status/recurrence and the complete source row. Tracker episodes and their ordered status/room events are imported losslessly; recurrence expansion remains. |
| `drugs`, `drug_inventory`, `drug_sales` | `inventory_products`, `inventory_lots`, `inventory_transactions` | Product and lot configuration, current warehouse balances, expiration/destruction metadata, and every historical sale or stock movement are preserved with their complete source rows. New dispensing uses row locks, FEFO allocation and atomic no-negative-stock enforcement. |
| `facility`, provider `users`, warehouse `list_options`, `users_facility` | `facilities`, `practitioners`, `warehouses`, `practitioner_facility_access`, `user_facility_access` | Facility and provider attributes retain full source payloads. Historical provider assignments are preserved independently from modern login linkage; active user grants use normalized foreign keys and opt-in access semantics. |
| Legacy report result pages and `report_results` workflows | `report_runs` plus domain read models | Each migrated execution stores normalized parameters, ordered columns, JSON-safe rows, totals, row count, actor, timestamp and a deterministic SHA-256 checksum; CSV is generated from that immutable snapshot. |
| `form_encounter`, `forms`, `form_*`, LBF tables, `esign_signatures` | Encounter/form models and `clinical_signatures` | Installed form payloads are retained generically, with typed core forms. Modern form/encounter signing requires password reauthentication and stores content hashes, separate chained evidence, signer snapshots, attestations and amendments; PostgreSQL rejects signature updates/deletes. Encounter locks prohibit later form creation or edits. Original legacy hashes and payloads remain available for reconciliation; specialized typed editors remain. |
| `lists`, `immunizations`, `prescriptions`, `form_vitals` | Clinical models | Maintain codes, dates, verification/status, encounter links and provenance |
| `procedure_*` | Order/specimen/result/report models | Preserve parent/line relationships and review state |
| `documents`, `categories*`, `documents_legal_*` | Document models and `patient_photos` | General documents remain private by default. Recognizable JPEG/PNG/BMP content assigned to the protected `Patient Photograph` category is also imported as versioned photo data with source document ID, source metadata, SHA-256, byte count and one deterministic primary image per patient. Unavailable filesystem/encrypted content is rejected for explicit remediation. Category hierarchy, object storage, templates and legal evidence remain. |
| `insurance_*`, `eligibility_verification`, `billing`, `claims`, `ar_*`, payment tables | Financial models | Decimal-exact amounts, priorities, diagnoses, claim identifiers and ledger balancing are cutover gates |
| `drugs`, `drug_inventory`, `drug_sales` | Inventory models | Stock changes must be transactional and reconcile per warehouse/lot |
| `api_token`, `api_refresh_token`, OAuth client/token tables | `auth_sessions`, future OAuth client/grant models | Legacy bearer and refresh credentials are never imported. New staff and portal sessions store only refresh-token SHA-256 digests, rotate access identifiers, detect one-generation replay and support immediate revocation; client grants/scopes remain to be migrated. |
| `login_mfa_registrations` | `mfa_registrations`, `mfa_challenges` | Legacy MFA ciphertext is not decryptable without source installation keys and is never treated as a usable credential. Staff re-enroll TOTP; new seeds use authenticated encryption, recovery codes are stored only as digests, and challenges are bounded and auditable. U2F/WebAuthn migration remains pending. |
| Portal-visible laboratory results, documents and encounter forms | nullable `released_to_patient_at` / `released_by_id` fields; `identity_audit_events` | Imported clinical records remain private by default. Release is an explicit modern workflow and is never inferred from legacy presence alone. Portal reads are patient-bound and recorded against the portal account; legacy portal activity can be retained separately during import until a verified event mapping is available. |
| Portal ledger and gateway audit | claim release fields; `payment_intents`; confirmed `claim_payments` | Imported claims remain portal-private until staff release them. Idempotency keys, request fingerprints, state and processor references are retained; gateway tokens, PAN and CVV are never stored. A `claim_payment` is created only for a confirmed successful intent. Detailed legacy allocations, adjustments and unapplied credits remain a separate reconciliation phase. |
| Portal reset/MFA credentials | `portal_password_reset_tokens`, `portal_mfa_registrations`, `portal_mfa_challenges` | Legacy reset tokens, password verifiers and MFA secrets are never imported. Patients receive new one-use reset links and enroll new encrypted TOTP seeds. Portal tables cannot reference staff identities and all pre-existing portal sessions are revoked on successful recovery. |
| `audit_master`, `audit_details`, `log` | Immutable audit event/detail | Retain actor, patient, event, before/after detail and timestamps with tamper evidence |
| `background_services`, `email_queue` | Job/schedule/outbox models | Preserve enabled state/schedule; import queued PHI only into secured outbox |

Every remaining source table and field is presently **unmapped, not obsolete**.
The generated schema manifest used by the zero-omission audit will be versioned
with the migration as table-level adapters are completed.
